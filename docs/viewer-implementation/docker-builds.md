# Single-app Docker builds

- The repository root `tsconfig.json` is an aggregate TypeScript solution that references every SvelteKit app and each app's generated `.svelte-kit/tsconfig.json`.
- Each app Dockerfile uses the repository root as its build context but builds only one app. After `COPY . .`, remove the aggregate `tsconfig.json` from the build stage, run `svelte-kit sync` only for the target app, and then run that app's build. Otherwise a clean build can fail while resolving another app's missing generated tsconfig.
- Keep the aggregate `tsconfig.json` available for local and CI workspace-wide checks; this is a container-only workaround for single-app image builds.
- The pattern is implemented in `apps/account-site/Dockerfile`, `apps/content-site/Dockerfile`, `apps/media-lab-site/Dockerfile`, and `apps/tools-site/Dockerfile`.
- `pnpm verify:adapter-node-build` rebuilds all four apps and checks for empty adapter-node server chunks, generated runtime configuration, importable request handlers and route nodes, and content-site client retention for Howler and EventDebugDialog.
- Adapter-node 6 no longer consumes the runtime `ORIGIN` variable. With `paths.origin` unset, it derives each request origin at runtime (`node_modules/@sveltejs/adapter-node/src/handler.js`, `get_origin`): the protocol comes from the header named by `PROTOCOL_HEADER` and falls back to `https` when that variable or header is absent, and the host comes from `HOST_HEADER`, falling back to `Host`. A request with no host gets a 400.
- Origin decisions (confirmed by the repository owner, 2026-10-31):
  - One image serves test and production, so `paths.origin` stays unset; a build-time origin would make the production image a different artifact from the one validated in test.
  - Set `PROTOCOL_HEADER=x-forwarded-proto` through the deployment values of each environment (it is environment-owned because it trusts the ingress in front of the pods). `HOST_HEADER`, `PORT_HEADER`, `ADDRESS_HEADER`, and `XFF_DEPTH` stay unset: nothing in `apps/*/src` calls `getClientAddress`, and the `Host` header already carries the public host.
  - Production sits behind Cloudflare in Full (strict) mode with the NGINX Ingress as the origin, so the ingress hop is HTTPS and the header it forwards is `https`. Switching Cloudflare to a mode that reaches the origin over HTTP would make the derived origin `http` and must be re-checked first.
  - The content-site is served from the production apex domain; tools-site, media-lab-site, and account-site use their own subdomains.
- Origin-dependent behavior to re-check after any proxy change: `og:url` and the Discord embed links built from `url` in `apps/content-site/src/lib/seo/discord-embed.ts`, and the three `POST` endpoints (`/api/gacha/:region/:id/pull`, `/music/:region/:id/download/progress`, `/event/:region/:id/bgm/progress`). The media-lab-site service worker (`static/sw.js`, registered at scope `/`) is per origin and takes its asset allowlist from the page at runtime, so it needs no origin configuration; users get a fresh cache on a new domain.
- The pod probe endpoint is `GET /healthz` on every app (`apps/*/src/routes/healthz/+server.ts`). It returns `200 ok` with `Cache-Control: no-store` and makes no upstream calls; `scripts/verify-docker-image.mjs` asserts both in CI.
